## 1. Резюме проекта

**Eduxa** — клиент-серверная веб-CRM для учебных центров (курсы, языковые школы, репетиторские центры), закрывающая полный цикл:

- захват и конверсия лидов;
- управление курсами, группами, расписанием;
- учёт студентов, посещаемости, оценок и экзаменов;
- финансовый учёт (биллинг студентов, зарплаты преподавателей, P&L);
- multi-branch (мультифилиальность) с изоляцией данных;
- уведомления родителям через Telegram-бота в реальном времени.

Два независимых интерфейса: **Admin/SuperAdmin** (полный доступ) и **Teacher** (изолированный, только свои группы/студенты).

## 2. Рекомендуемый технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Frontend | **Next.js (React) + TypeScript** | SSR для дашбордов, файловая маршрутизация, хорошая DX |
| UI-кит | **Tailwind CSS + shadcn/ui** | Быстрая сборка форм/таблиц, легко кастомизировать тему (light/dark) |
| Графики | **Recharts** | Линейные/круговые графики из ТЗ (динамика, посещаемость) |
| State/data | **TanStack Query (React Query) + Zustand** | Кэш серверных данных, локальный UI-стейт (выбранный филиал, тема) |
| Backend | **NestJS (Node.js/TypeScript)** или **Django REST Framework** | Модульная архитектура 1:1 ложится на модули ТЗ (Teachers, Courses, Groups…) |
| База данных | **PostgreSQL** | Реляционная целостность важна для финансов; поддержка Row-Level Security для изоляции по филиалам |
| ORM | **Prisma** (Node) / **Django ORM** | Миграции, типобезопасность |
| Очереди/фон. задачи | **Redis + BullMQ** | Массовые рассылки, пересчёт биллинга, автогенерация расписания |
| Real-time | **WebSocket (Socket.io)** | Мгновенное обновление дашборда, статусов заявок на привязку Telegram |
| Telegram-бот | **Telegraf.js** (или python-telegram-bot) | Отдельный сервис/воркер, общается с backend через внутренний API |
| Файлы (логотип и т.п.) | **S3-совместимое хранилище (MinIO/AWS S3)** | Ограничения PNG/JPG, 256×256, до 5 МБ проверяются на бэкенде |
| Аутентификация | **JWT (access + refresh) + bcrypt/argon2** | Токены аннулируются на logout, роль зашита в payload |
| Инфраструктура | **Docker + Docker Compose**, затем Kubernetes при росте | Изолированные сервисы: web, api, bot, db, redis |
| CI/CD | **GitHub Actions** | Линт → тесты → билд → деплой |
| Мониторинг | **Sentry (ошибки) + Grafana/Prometheus или Uptime Kuma** | Критично из-за денежных операций |

> Это ориентир, а не догма — стек можно заменить на знакомый команде (например, Laravel + Vue), но **сохраняйте принципы**: строгая типизация, миграции, очереди для тяжёлых/массовых операций, разделение bot-сервиса от основного API.

## 3. Архитектура системы

```
                         ┌───────────────────────┐
                         │   Web Client (Next.js)│
                         │  Admin UI / Teacher UI│
                         └──────────┬────────────┘
                                    │ REST/WebSocket (JWT)
                         ┌──────────▼────────────┐
                         │      API Gateway /     │
                         │     Backend (NestJS)   │
                         │  ── Auth/RBAC          │
                         │  ── Teachers           │
                         │  ── Courses/Groups     │
                         │  ── Leads/Students     │
                         │  ── Attendance         │
                         │  ── Exams              │
                         │  ── Finance/Reports    │
                         │  ── Announcements      │
                         │  ── Settings/Branches  │
                         └──┬───────────┬─────────┘
                            │           │
                  ┌─────────▼───┐   ┌───▼────────────┐
                  │ PostgreSQL  │   │  Redis (queue)  │
                  │ (branch_id  │   │  + BullMQ jobs  │
                  │  на всех    │   └───┬─────────────┘
                  │  таблицах)  │       │
                  └─────────────┘       │
                                        │
                         ┌──────────────▼─────────────┐
                         │   Telegram Bot Service      │
                         │   (Telegraf, отдельный      │
                         │    процесс/контейнер)       │
                         │  ── /start, привязка ID     │
                         │  ── push-уведомления        │
                         │  ── запросы родителя        │
                         └─────────────────────────────┘
```

**Ключевые архитектурные решения:**

- **Мультифилиальность** реализуется через колонку `branch_id` на всех бизнес-таблицах + middleware, который автоматически подставляет фильтр по выбранному в шапке филиалу (или снимает фильтр при выборе «Barcha filiallar»).
- **Bot-сервис — отдельный процесс**, который не блокирует основной API: события (посещаемость сохранена, оплата принята, экзамен опубликован) публикуются в очередь Redis, а bot-воркер их разбирает и шлёт сообщения. Это защищает CRM от зависаний Telegram API.
- **WebSocket** нужен минимум в двух местах: обновление счётчиков на Dashboard в реальном времени и появление новой карточки в «Ulanish So'rovlari» (заявки на привязку родителя) без перезагрузки страницы.

## 4. Модель данных

Ниже — минимальный набор таблиц/сущностей, покрывающий всё ТЗ. На старте разработки стоит оформить это в виде ER-диаграммы и Prisma-схемы/миграций.

| Таблица | Ключевые поля | Связи |
|---|---|---|
| `branches` | id, name, address, is_main | 1—M со всеми бизнес-таблицами |
| `users` | id, login, password_hash, role (`super_admin/admin/teacher`), branch_id | — |
| `teachers` | id, user_id, first_name, last_name, phone, salary_type (`fixed/per_student/percent`), kpi_rate, salary_balance | 1—M `groups` |
| `courses` | id, title, description, duration, price_per_month | 1—M `groups` |
| `rooms` | id, name, branch_id | 1—M `groups` |
| `groups` | id, name, course_id, teacher_id, room_id, weekdays[], time, start_date, end_date (расчётное) | M—M `students` через `group_students` |
| `students` | id, student_code (`ST101`), first_name, last_name, birth_date, phone, address, parent_name, parent_phone, status (`active/frozen/graduate`), balance | M—M `groups` |
| `group_students` | group_id, student_id, joined_at, status (`active/graduate`) | связующая таблица |
| `leads` | id, full_name, phone, interested_course_id, teacher_id, status (`new/contacted/callback/trial/converted`), comment | → `students` при конверсии |
| `attendance` | id, group_id, student_id, date, status (`came/excused/absent`), rating (1–5), homework_done (bool), comment | триггерит биллинг и Telegram |
| `transactions` | id, student_id?, teacher_id?, branch_id, type (`income/expense`), category, amount, comment, created_at | лог KIRIM-CHIQIM |
| `exams` | id, group_id, name, date, max_score | 1—M `exam_results` |
| `exam_results` | id, exam_id, student_id, score, comment, rank (расчётное) | — |
| `announcements` | id, target_type (`all/group/course`), target_id, title, body, delivery_status | лог рассылок |
| `telegram_links` | id, telegram_chat_id, student_id, status (`pending/active/rejected`), requested_at | связывание родителя |
| `notification_log` | id, telegram_link_id, trigger_type, payload, sent_at | аудит push-уведомлений |
| `branch_settings` | branch_id, billing_mode (`daily/monthly`), logo_url, center_name | White Label |

**Важные производные значения** (не хранить статично, считать на лету или пересчитывать job'ом):

- `students.balance` = сумма оплат − сумма списаний (см. раздел 8).
- `teachers.salary_balance` = накопленный KPI с момента последней выплаты.
- `end_date` группы = `start_date` + `courses.duration`.

## 5. Ролевая модель и авторизация (RBAC)

| Роль | Доступ |
|---|---|
| **Super Admin** | Все филиалы, все модули, настройки White Label, управление сотрудниками |
| **Admin** | Доступ ограничен своим филиалом (если не выдан доступ «Barcha filiallar») |
| **Teacher** | Только свои группы/студенты/расписание/посещаемость/экзамены/рейтинг. Нет доступа к лидам, финансам, настройкам, логам |

**Практическая реализация:**

1. JWT payload содержит `user_id`, `role`, `teacher_id` (если применимо), `branch_id`.
2. На backend — guard/middleware, который для роли `teacher` **принудительно** добавляет фильтр `WHERE teacher_id = :currentTeacherId` на уровне запроса к БД, а не только скрывает кнопки на фронте. Скрытие в UI — это UX, а не безопасность.
3. Прямые обращения к внутренним URL без валидного токена — 401/403 на уровне middleware, до контроллера.
4. Read-only блокировка посещаемости преподавателем после сохранения администратором реализуется проверкой: если запись `attendance` за эту дату уже существует и создана `admin`, поле `locked_by_admin = true` — фронт получает флаг и рендерит форму как disabled.

## 6. Модули панели администратора

### 6.1 Dashboard
Метрики за выбранный филиал (или агрегат): месячная/суммарная выручка, активные студенты, должники, группы, преподаватели, конверсия лид→студент. Графики: линейный (движение денег за 6 мес.), круговой (посещаемость).

### 6.2 Преподаватели
Форма: имя, фамилия, телефон (+998), тип оплаты (фикс/сумма за студента/% KPI), авто-логин/пароль. Карточка преподавателя показывает текущий KPI-баланс и список групп.

### 6.3 Курсы
CRUD каталога: название, описание, длительность, цена за месяц. Карточки-плитки.

### 6.4 Группы
Форма привязки курса + преподавателя + дней недели + времени + аудитории + даты старта. Авторасчёт даты окончания. Внутри группы — вкладки «Активные»/«Выпускники» и контекстное меню (заморозка, перевод, отвязка, возврат в лиды).

### 6.5 Расписание
Авто-генерация сетки на основе параметров активных групп + ручное добавление. Режимы «Карточки»/«Календарь».

### 6.6 Лиды
Воронка со статусами `Новый → Контакт → Повторный звонок → Приглашён на пробный → Зарегистрирован`. При переходе в «Зарегистрирован» — подтверждение и автоматический перенос в студенты.

### 6.7 Студенты
Реестр с ID вида `ST101`, вкладки «Активные»/«Архив», импорт/экспорт CSV, PDF-список. Функции в действиях: история оценок, генерация токена для Telegram, заморозка (останавливает посещаемость и биллинг).

### 6.8 Посещаемость
Выбор группы + даты, три статуса (пришёл/уваж. причина/неуваж.), рейтинг 1–5 звёзд, отметка ДЗ, комментарий. Сохранение → списание баланса (если применимо) + push родителю.

### 6.9 Экзамены
Шаблон текста уведомления с переменными `{studentName} {examName} {score} {maxScore} {totalStudents} {rank}`. Ввод баллов по группе, архив истории со средним/макс/мин.

### 6.10 Сотрудники (Admin)
Управление учётками персонала (роль, филиал). Преподаватели синхронизируются автоматически.

### 6.11 Рассылки
Таргетинг: все родители / конкретная группа / конкретный курс. Заголовок + текст → пакетная отправка в Telegram API, статус `BOT_DELIVERED`.

### 6.12 Отчёты
5 вкладок: динамика поступлений, ведомость задолженностей, академическая посещаемость, аналитика экзаменов, книга **KIRIM-CHIQIM** (доходы/расходы, чистая прибыль = доходы − расходы). Экспорт Excel/CSV/PDF везде.

### 6.13 Настройки центра
White Label: логотип (PNG/JPG, 256×256, ≤5 МБ), название системы, режим биллинга (поурочный/помесячный), управление филиалами.

## 8. Финансовая и KPI-логика

### 8.1 Поурочный биллинг (при `billing_mode = daily`)

```
цена_урока = цена_курса_за_месяц / количество_занятий_в_месяце_по_графику_группы
```

- Списание происходит **в момент сохранения посещаемости**.
- Статус `Keldi` (пришёл) или `Sababsiz` (неуваж. причина) → списывается `цена_урока`, пишется запись в `transactions` (CHIQIM/списание с баланса студента).
- Статус `Sababli` (уваж. причина) → баланс не трогается.

```
баланс_студента = сумма_оплат − сумма_списаний
статус: баланс >= 0 → "Ortiqcha" (профицит)
        баланс <  0 → "Qarz" (долг) → попадает в ведомость должников
```

### 8.2 KPI преподавателя (пример: ставка 80%)

```
S_преп = цена_урока × (KPI_ставка / 100)
```

Начисляется на виртуальный баланс преподавателя при каждом списании со статусом `Keldi`/`Sababsiz`. При выплате (`Oyliklar → To'lash`) баланс обнуляется, а в `transactions` создаётся запись `CHIQIM`, категория `Xodimlari maoshi`.

> **Совет:** вынесите этот расчёт в отдельный доменный сервис (`BillingService`) с юнит-тестами — это код, который трогает деньги, и баги здесь дороже всего.

## 9. Интеграция Telegram-бота

### 9.1 Привязка аккаунта родителя

1. `/start` → приветствие + меню.
2. Кнопка «Привязать ребёнка» → бот запрашивает `Student ID` (например, `ST101`).
3. Бот проверяет ID через внутренний API CRM → создаёт запись `telegram_links` со статусом `pending`.
4. В CRM (модуль «Заявки на привязку») администратор видит карточку в реальном времени (WebSocket) и подтверждает/отклоняет.
5. После подтверждения → статус `active`, родителю приходит push об успехе.

### 9.2 Команды меню бота

| Кнопка | Что возвращает |
|---|---|
| Посещаемость | Статус за сегодня + сводка за неделю/месяц |
| Оплаты | Стоимость курса, баланс, сумма долга |
| Домашние задания | Лог выполнения по датам |
| Рейтинг | Позиция в leaderboard, количество звёзд |
| Экзамен | Последний результат с местом в группе |

### 9.3 Триггеры push-уведомлений

| Событие в CRM | Получатель | Когда |
|---|---|---|
| Пропуск без причины | Родитель | При сохранении посещаемости со статусом `Sababsiz` |
| Невыполненное ДЗ | Родитель | При отметке крестика в посещаемости |
| Результат экзамена | Родитель | При сохранении баллов |
| Оплата принята | Родитель | При добавлении платежа |
| Напоминание о долге | Родитель | Ручной триггер администратора |
| Объявление | Все/группа/курс | При рассылке |

> Все уведомления должны идти **через очередь** (BullMQ), а не синхронным вызовом внутри HTTP-запроса — иначе таймауты Telegram API будут подвешивать сохранение посещаемости или оплаты.

## 10. Безопасность

- Пароли — только хэшированные (bcrypt/argon2), никогда в открытом виде в БД или логах.
- JWT access (короткий TTL) + refresh (httpOnly cookie), полная инвалидация при logout.
- Жёсткая server-side проверка роли на **каждом** эндпоинте, не полагаться на скрытие UI-элементов.
- Изоляция данных преподавателя — обязательный фильтр на уровне запроса к БД (см. раздел 5), в идеале — Postgres Row-Level Security как второй рубеж защиты.
- Валидация загрузки логотипа (тип файла, размер, реальный MIME, а не только расширение).
- Rate limiting на auth-эндпоинты и на Telegram webhook.
- Логирование финансовых операций (кто, когда, что изменил) — отдельная audit-таблица.
- HTTPS везде, CORS ограничен доменом фронтенда.

## 11. Нефункциональные требования

- **Локализация**: узбекский (латиница) как основной язык интерфейса; продумать возможность i18n на будущее.
- **Валюта**: UZS, форматирование с разделителями разрядов.
- **Часовой пояс**: Asia/Tashkent по умолчанию.
- **Даты**: единый формат на всё приложение (в ТЗ встречаются и `YYYY-MM-DD`, и `MM/DD/YYYY` — унифицируйте на этапе проектирования, разночтения в датах — частый источник багов).
- **Производительность**: пагинация и серверная фильтрация везде, где список может расти (студенты, транзакции, лиды).
- **Резервное копирование**: ежедневный бэкап БД, хранение ≥ 30 дней.
- **Наблюдаемость**: логирование ошибок (Sentry), метрики очередей (сколько сообщений не доставлено в Telegram).

## 12. Дорожная карта разработки

Ориентировочная разбивка на этапы (сроки зависят от размера команды — приведены как логическая последовательность, а не жёсткий дедлайн):

**Этап 0 — Фундамент**
Схема БД, авторизация/RBAC, базовый CRUD филиалов и пользователей, каркас UI (тема, layout, роутинг ролей).

**Этап 1 — Учебный контур (MVP)**
Курсы → Преподаватели → Группы → Расписание → Студенты → Посещаемость (без биллинга). Цель: центр может вести учёт без денег.

**Этап 2 — Финансы**

## 13. Деплой и инфраструктура

- **Docker Compose** для локальной разработки и staging: контейнеры `web`, `api`, `bot`, `postgres`, `redis`.
- Отдельные `.env` для dev/staging/prod, секреты — через менеджер секретов (Doppler/Vault/GitHub Secrets), никогда в git.
- CI: линт + типы + unit-тесты (обязательно для `BillingService` и `KpiService`) на каждый PR.
- CD: автодеплой staging при мерже в `develop`, ручной approve для `main` → prod.
- Миграции БД — только через ORM-миграции, без ручных `ALTER TABLE` на проде.
- Telegram webhook должен указывать на публичный HTTPS-эндпоинт бот-сервиса (или long polling на старте, если нет домена/SSL).

## 14. Советы Senior-разработчика

1. **Сначала контракт API, потом фронт.** Опишите эндпоинты в OpenAPI/Swagger до вёрстки экранов — избавит от бесконечных «а поле переименовали».
2. **Деньги = тесты.** Формулы биллинга и KPI покройте unit-тестами с граничными случаями (0 занятий в месяце, отрицательный баланс, деление на ноль в расчёте цены урока).
3. **Идемпотентность списаний.** Защитите повторное сохранение посещаемости от двойного списания (уникальный constraint на `attendance(group_id, student_id, date)`).
4. **Не считайте `end_date` группы триггером** — пересчитывайте её при каждом изменении `start_date` или курса, а не храните «навсегда».
5. **Изоляция филиалов — на уровне БД-запроса**, а не только UI-фильтра, иначе легко получить утечку данных между филиалами.
6. **Очереди для всего, что «летит наружу»** (Telegram, email, экспорт больших PDF) — не блокируйте основной поток запроса.
7. **Сид-данные и demo-режим** сильно ускорят приёмку заказчиком — заранее подготовьте скрипт наполнения тестовыми филиалами/группами/студентами.
8. **Аудит-лог для финансовых и ролевых изменений** — рано или поздно кто-то спросит «кто изменил баланс».
